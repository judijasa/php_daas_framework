# DB instance created by ema; manual reuter.ini — Plan & Progress

Date: 2026-09-09
Repos: php_daas_framework (this repo); ../ema (upstream).
       Consumer-side config-repo and wiring changes are tracked in each
       consumer's own dated plan doc.

## Decision

Move MariaDB instance provisioning out of framework deploy-time and into
database-creation time, with **one instance per database**. `ema create`
(prod) now provisions the instance — datadir, `/etc/<instance>/my.cnf`,
`mariadb@<instance>` systemd unit, an auto-picked TCP port — before creating
the database and applying its schema packages, then **returns the
connectivity values** (`SERVER`/`PORT`/`MYSQL_UNIX_PORT`/dbname) for the
operator to record. `reuter.ini` becomes a manually-maintained,
consumer-owned file (committed in the consumer's config repo) instead of
being generated by `gen-reuter`.

The framework no longer provisions MariaDB and no longer generates
connectivity. `pf-deploy` instead runs a **warn-only** `db-check` (never
self-heals): a socket-based instance+`information_schema` check on the
`db:`-tagged host, and a TCP-reachability check per `reuter.ini` section on
every host. `DEPLOY_DB_*` is removed; the `db:<name>` tag survives only as
the advisory anchor that `db-check` and the one-to-one server constraint use.

Out of scope here: the service-account auth policy (passwords vs. client
certs) and the consumer's config-repo wiring — both deferred to open items /
the consumer's own plan.

This supersedes the DB-provisioning side of
`doc/plans/2026-08-22-multi-server-deploy.md` and the `MYSQL_*`/instance
parts of `doc/plans/2026-08-24-env-prod-merge-into-deploy-conf.md`, and builds
on the schema-only `ema create` from
`doc/plans/2026-09-07-ema-schema-only-and-service-users.md`.

## Phases

1. **ema: instance creation at `create` time + value emission.** `ema create`
   becomes self-provisioning; `ema values <db>` recovers a lost record.
2. **framework: stop deploy-time provisioning; manual reuter.ini.** Remove
   `pf-provision`'s DB block, `DEPLOY_DB_*`, and `gen-reuter`; `gen-env`
   projects `REUTER_INI` from a new consumer key.
3. **framework: warn-only deploy checks.** New `db-check` (socket + TCP),
   called by `pf-deploy`.
4. *(decision, parallel)* service-account auth policy — open item below.

Phase 2 depends on Phase 1 (the manual file is only writable once `create`
emits values); Phase 3 depends on Phase 2 (it reads the manual reuter.ini).
Nothing is in production yet, so no live-host migration ordering is involved.

## Mechanism & data ownership

| Owner | What it produces |
|---|---|
| ema (`ema create`) | instance + database + schema packages + connectivity values |
| ema (`ema values <db>`) | connectivity values for an existing database (recovery) |
| consumer (config repo) | manually-recorded `reuter.ini` `[<dbname>]` sections |
| framework (`db-check`) | warn-only deploy verification (socket + TCP), never repair |

## Changes

### ema (../ema)

#### Phase 1 — instance creation at `create` time

- [x] `ema` — `_cmd_create` (prod): provision the per-database instance when
      absent before creating the database — datadir under the instance base,
      write `/etc/<instance>/my.cnf`, install + `enable --now`
      `mariadb@<instance>` (root; systemd for boot durability), then run
      `mariadb-install-db` and create the database + schema deps against it.
- [x] `ema` — port allocation: pick once with a `get_free_port`-style kernel
      ephemeral bind, persist to the instance `my.cnf` and the returned
      values; verify (`ss`/bind) with a retry loop at start; never re-pick on
      a running instance.
- [x] `ema` — `_cmd_create` returns the section shape (`SERVER`/`PORT`/
      `MYSQL_UNIX_PORT`/dbname) on success.
- [x] `ema` — new `ema values <db>` verb: resolve an existing database's
      instance and print the same section values (recovery).

### php_daas_framework (this repo)

#### Phase 2 — stop deploy-time provisioning; manual reuter.ini

- [x] `bin/pf-provision.sh` — remove the MariaDB block (base dir, defaults
      file, systemd unit, `mariadb-install-db`, start); keep `PROD_USER`
      assertion and the log/deploy dirs.
- [x] `bin/pf-deploy.sh` — drop `DEPLOY_PROVISION_DB=1`/`DEPLOY_DB_BIND`
      passing and the DB-host provisioning gate; drop `DEPLOY_DB_BASE` from
      `require_config`.
- [x] `bin/gen-reuter` — remove (reuter.ini is now manual).
- [x] `bin/fetch-private-data` — add `reuter.ini` to the injected private files
      (required, like `machines.ini`), so the manually-maintained consumer
      reuter.ini lands in the consumer's `etc/`.
- [x] `bin/gen-env` — stop deriving `REUTER_INI` from `DEPLOY_DB_INSTANCE`;
      emit it from a new `DEPLOY_REUTER_INI` deploy.conf key, failing loudly
      when unset.
- [x] `etc/deploy.conf.template` — remove `DEPLOY_DB_BASE`/`DEPLOY_DB_INSTANCE`
      /`DEPLOY_DB_PORT`/`DEPLOY_DB_BIND`; add `DEPLOY_REUTER_INI`; rewrite DB
      comments for the create-at-ema model.
- [x] `etc/machines.ini.template` — redefine `db:<name>` as the advisory
      `db-check` anchor (not "gets an instance during provisioning").

#### Phase 3 — warn-only deploy checks

- [x] `bin/db-check` (new) — warn-only: on a `db:`-tagged host, enumerate
      `mariadb@*` units, read each `socket=` from `/etc/<instance>/my.cnf`,
      `mysqladmin --socket ping`, and query `information_schema.SCHEMATA` for
      each declared `db:<name>`; on every host, TCP-connect each `reuter.ini`
      section's `SERVER:PORT`. Warn on any miss; never repair.
- [x] `bin/pf-deploy.sh` — invoke `db-check` in the server steps (after
      `gen-env`), warn-only.
- [x] `README.md` — replace the "Multiple MariaDB instances on one server"
      section and the deploy-chain DB paragraphs (ema-owned instances, manual
      reuter.ini, `db-check`).
- [x] `doc/system/ema.md` — rewrite deploy chain + reuter.ini contract
      (manual, section-per-db, values from `ema create`).

## Open items

- **Service-account auth policy — undecided.** Accounts `admin`/`reader`/
  `public` (consumer-owned) currently use `<ACCOUNT>_PASSWORD` keys.
  Passwordless + client cert (`REQUIRE SUBJECT`, like team members) would
  remove the shared-secret-from-repo problem entirely, but the team-member
  precedent already assumes server-side TLS (`ssl-ca`/`ssl-cert`/`ssl-key`)
  which is still a pending ema-side piece. Passwords stay **for now**; the
  decision and any reuter.ini key-shape change wait on this.
- **`DEPLOY_REUTER_INI`** is the proposed key name; confirm it and decide how
  the consumer ships the manual reuter.ini to every host (config-repo
  injection vs. archive) — consumer-side, its own plan.
- **Port range vs. firewall/ZeroTier** allow rules: the kernel ephemeral band
  may sit outside the overlay firewall rules; a reserved per-network range is
  likely needed.
- **Server-side TLS** (`ssl-ca`/`ssl-cert`/`ssl-key` in the MariaDB config) is
  a prerequisite for *any* client-cert account (team or service) — pending
  ema work, not yet tracked here.
- Consumer config-repo (reuter.ini) and deploy-wrapper changes are **not**
  tracked here; they belong in the consumer's own dated plan doc.
